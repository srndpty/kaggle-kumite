## コンペ概要

**EC 企業の商品を、匿名化された93個の数値特徴から9つの商品カテゴリに分類するコンペ。**

- 主催: Otto Group（ドイツの大手 EC・通販グループ。世界各国に子会社を持ち、膨大な数の商品を扱う）
- 背景: 国や子会社ごとにシステムが異なるため、同じ商品が別々のカテゴリに分類されてしまうことが多い。商品分析の質は、似た商品を正しくまとめられるかに大きく左右されるため、商品を自動で正しいカテゴリに振り分けるモデルが求められた
- 予測するもの: 各商品が9つの主要カテゴリ（ファッション、電子機器などの大分類）のどれに属するか。ラベルを当てるのではなく、9カテゴリそれぞれの確率を出す
- 入力: 1行 = 1商品。93個の特徴量は商品に関するさまざまなイベントの回数だが、意味は伏せられている。カテゴリ名も Class_1〜Class_9 に置き換えられている
- 開催: 2015年3月〜2015年5月18日（Featured、賞金総額 $10,000）。`kaggle competitions leaderboard --download` で取得した Public Leaderboard は 3,509 行（2026-11-15 取得）。レビューでは、コンペ公式ページの表示は 3,507 チームとの指摘があった（当方では未確認。取得時点や数え方の違いと考えられる）。本文の順位相当はすべて 3,509 行の Leaderboard に対するもの
- 位置づけ: 特徴量の意味がわからないため、ドメイン知識が使えない。モデルの選び方・検証・確率の扱いだけで勝負する、純粋な表形式の多クラス分類
- 参考スコア（Public Leaderboard）: 1位 0.38055、上位10% 0.42907、中央値 0.54175。当リポジトリの E01（0.45008）は 709 位相当（Late Submission なので正式な順位ではない）

出典について: 主催者・背景・カテゴリの例は、Kaggle Overview の説明文を記憶に基づいて要約したもの（ページは JavaScript で描画されるため、本文を CLI では取得できなかった）。期間の終わりとチーム数・スコアは、`kaggle competitions leaderboard --download` で取得した Public Leaderboard から確認した。賞金はカタログの記載による。

# H1: log1p 変換（features.py）。行ごとに完結する変換なので、CV の外で train/test に適用してよい
def log1p(df):
    return df[FEATURES].astype("float64").transform(np.log1p)


# H1: 線形モデル（models.py）。標準化は Pipeline 内で学習 fold だけを使って fit する
model = make_pipeline(StandardScaler(), LogisticRegression(C=1.0, max_iter=2000))

# H2: クラス別の損失（analyze.py）。各サンプルの「正解クラスの予測確率」の -log を正解クラスごとに集計する
sample_loss = -np.log(np.clip(oof[np.arange(len(y)), y], EPS, 1))
contribution = [sample_loss[y == k].sum() / sample_loss.sum() for k in range(9)]

# H3: 行集約特徴（features.py）
x.assign(row_sum=x.sum(axis=1), row_nnz=(x > 0).sum(axis=1))


# H4: 温度スケーリング（calibrate.py）。fold k の T は、k 以外の fold の OOF で決める（クロスフィット）
def apply_temperature(pred, t):
    return softmax(np.log(np.clip(pred, EPS, 1)) / t, axis=1)


for fold in range(N_SPLITS):
    tr, va = folds != fold, folds == fold
    t = fit_temperature(y[tr], oof[tr])
    calibrated[va] = apply_temperature(oof[va], t)

### H1: log1p 変換

| 比較 | fold ごとの差 | 平均 | 改善 fold |
|---|---|---:|---:|
| E02 → E03（ロジスティック回帰） | -0.0077 -0.0055 -0.0096 -0.0111 +0.0033 | -0.0061 | 4/5 |
| E01 → E04（LightGBM） | -0.00001 0 0 0 +0.00001 | 0.0000 | — |

- 線形モデルでは改善したが、OOF 0.641 → 0.635 と幅は小さい。標準化だけでも裾の影響はある程度抑えられていたと考えられる
- LightGBM は best iteration まで E01 と同じで、差は浮動小数点の誤差の範囲。LightGBM は値の順序だけで分岐を作るので、単調変換は効かない（想定どおり）
- 線形モデル（0.635）は LightGBM（0.474）より大幅に悪い。特徴量間の相互作用が重要なデータと考えられる
- NN での効果は未検証

### H3: 行集約特徴

- E01 → E05 の fold ごとの差は +0.0014 +0.0005 +0.0032 -0.0031 -0.0007（平均 +0.0003）。改善した fold と悪化した fold が混在しており、効果は認められない
- 木モデルは、特徴量の組み合わせからこの程度の情報をすでに取り出せていると考えられる

### H4: 温度スケーリング（`src/calibrate.py E01 E06`）

- E01 の OOF は過信気味だった。確信度 0.7〜0.8 のビンでは正解率 0.715 に対して平均確信度 0.750。ECE は 0.0151
- 温度 T は fold ごとに 1.098〜1.113（T > 1 は確率を穏やかにする方向）。他の fold の OOF で T を決めるクロスフィットなので、OOF スコアに検証データの情報は漏れていない
- E01 → E06 の fold ごとの差は -0.0011 -0.0038 -0.0020 -0.0034 -0.0020。5 fold すべてで改善し、平均 -0.0025
- 注意: テスト予測は 5 モデルの平均で、すでに確率が穏やかになっている。単一モデルの OOF で決めた T をそのままかけると、テスト側では効きすぎる可能性がある
  - → Late で確認したところ、実際に悪化した（P5 参照）

## P5: CV と Late の差の原因

`src/averaging_check.py` で、train の中で提出と同じ状況を再現した。外側の各 fold を疑似テストとして取り置き、残りのデータで E01 と同じ手順（内側 4 fold の CV と early stopping）を行う。単一モデルどうしは学習データ量が同じなので、平均の効果だけを分けて測れる。

| 指標（外側 5 fold の平均） | logloss |
|---|---:|
| 内側 OOF（単一モデル、E01 の OOF に相当） | 0.48812 |
| 疑似テスト・単一モデル | 0.49015 |
| 疑似テスト・4 モデル平均（E01 の提出に相当） | 0.46931 |
| 疑似テスト・単一モデル + 温度 T | 0.48787 |
| 疑似テスト・4 モデル平均 + 温度 T（E06 の提出に相当） | 0.47017 |

- **平均の効果は -0.0208**（単一 0.49015 → 平均 0.46931）。E01 の CV と Late の差（-0.022）とほぼ同じ大きさ。fold モデルの平均が CV と Late の差の主要因であることを、独立した疑似テストで強く支持する。ただし同じ train を使った追加実験であり、学習量の違いや分布差の影響まで完全に切り分けたわけではない
- 内側 OOF と疑似テストの単一モデルの差は +0.0020。OOF は検証 fold で early stopping しているので、その分だけ楽観側に偏っている（P3 で書いた偏りの大きさの実測値）。分布の差はこれ以上は見られない
- **温度スケーリングは、単一モデルには -0.0023 で効くが、平均予測には +0.0009 で悪化する**。E06 の CV（-0.0025）と Late（+0.00075）の結果を、両方ともほぼそのまま再現した
  - 内側 OOF で決めた T は平均 1.093。一方、平均予測にとって最適な T は 1.026（疑似テストのラベルで求めた診断値）
  - モデルを平均すると確率が穏やかになり、過信の大半はそれで解消される。そこにさらに T をかけると、確率を穏やかにしすぎる

### わかったこと

- OOF は「単一モデルの予測」、提出は「fold モデルの平均」であり、評価しているものが違う。モデル間の比較には OOF を使ってよいが、OOF の絶対値は提出スコアを悲観的に見積もる（約 0.02 という大きさは、Otto のこの学習方式に限った値で、別のモデル・コンペには一般化できない）
- **較正などの後処理は、提出と同じ形の予測で決め、同じ形で評価しなければならない**。単一モデルの OOF で調整すると、平均予測では逆効果になりうる
- 今後の後処理は、この入れ子の枠組み（疑似テスト上の平均予測）で評価する

### 1 位解法の概要

- 3 段構成。1 段目で約 33 モデルと 8 種類の追加特徴を作り、2 段目で 3 モデル、3 段目で加重平均する
- 1 段目のモデルは、性質の異なるものを幅広くそろえている
  - RandomForest、ExtraTrees、ロジスティック回帰、多項ナイーブベイズ、libFM、XGBoost（複数の特徴量の組み合わせ）、NN（Lasagne・H2O、最大 120 回の bagging）
  - kNN を k = 2〜1024 で 10 本
  - 変換はモデルごとに使い分けている: log(X+1)、sqrt(X+3/8)、標準化、TF-IDF、X==0 の指標
- 追加特徴: 各クラスの最近傍までの距離（近傍 1・2・4 件、生・TF-IDF・t-SNE の各空間）、t-SNE（3 次元）、k-means のクラスタ、行の非ゼロ数
- 2 段目: XGBoost、NN、AdaBoost + ExtraTrees を、1 段目の予測と一部の追加特徴の上で学習する。全データで学習し、それぞれ 250〜600 回 bagging する
- 3 段目: `0.85 × XGB^0.65 × NN^0.35 + 0.15 × ET`（幾何平均と算術平均の組み合わせ）
- 1 段目は「常に同じ fold の分け方」で OOF を作っている。2 段目の CV（4 fold）は Leaderboard と非常によく相関した、と書かれている
- スコア: CV 約 0.3962、Public 0.38055、Private 0.38243

### 2 位・5 位解法の概要

- 2 位: 中心はスタッキング。生データと TF-IDF 変換したデータの 2 系統で、K-fold の OOF からメタ特徴を作る。2 段目は元の特徴とメタ特徴を合わせて学習する。kNN 系の手法は過小評価されている、と述べている
- 5 位: TF-IDF 変換と、モデルの予測から作った特徴を元の特徴に加え、XGBoost と 2 層 NN をそれぞれ 30 回 bagging して平均

### 自分の取り組みとの差分

| 観点 | 上位解法 | 自分（P4 まで） |
|---|---|---|
| モデルの数・種類 | 1 段目だけで約 33 モデル。木・線形・kNN・NN・NB・FM | LightGBM と線形の 2 種類 |
| 統合方法 | 多段のスタッキング + 加重平均 | なし（単一モデル） |
| 近傍の情報 | クラス別の最近傍距離を特徴に使う。kNN モデルも多数 | 使っていない |
| 変換 | log1p、sqrt(X+3/8)、TF-IDF、t-SNE をモデルごとに使い分け | log1p のみ（H1） |
| bagging | NN は 120〜600 回 | fold 平均（5 モデル）のみ |
| 共通していた点 | 線形・kNN・NN に log(X+1)、行の非ゼロ数、全モデルで同じ fold | H1、H3、`split_version` の固定 |

- H3（行の非ゼロ数）は単独の LightGBM では効かなかったが、1 位は 2 段目の入力として使っている。単体で効かない特徴でも、統合の段階では意味を持ちうる
- 上位解法は「1 つのモデルを磨く」より「誤り方の異なるモデルを多数そろえて統合する」ことに労力を割いている。特徴量の意味が伏せられていて、ドメイン知識で特徴を作れないコンペならではの戦略と考える

### 再現実験（H5・H6）

差分のうち効果が大きそうな 2 点を、変更を 1 つに絞って再現した。

| run | 内容 | OOF | E01 との差（fold ごと） | 平均 | 改善 fold |
|---|---|---:|---|---:|---:|
| E07 | kNN（k=32、距離重み、log1p + 標準化） | 0.58269 | +0.101 〜 +0.124 | +0.1088 | 0/5 |
| E08 | ExtraTrees（300 本、log1p） | 0.59506 | +0.114 〜 +0.132 | +0.1211 | 0/5 |
| E09 | E01 + kNN 距離特徴 27 列（H6） | 0.45890 | -0.0173 -0.0139 -0.0084 -0.0172 -0.0184 | -0.0150 | 5/5 |
| E10 | スタッキング: E01・E03・E07・E08 の OOF 36 列 → LightGBM（H5） | 0.44381 | -0.0337 -0.0319 -0.0230 -0.0306 -0.0314 | -0.0301 | 5/5 |

- **H6（kNN 距離特徴）**: 5 fold すべてで改善し、平均 -0.0150。best iteration は約 480 から約 200 に減った。距離特徴が強い手がかりになり、少ない木で済むようになったと考えられる
  - 実装は [`features.knn_dist`](src/features.py)。距離は log1p 空間で測り、各クラスについて近傍 1・2・4 件までの距離の和をとる（9 クラス × 3 = 27 列）

  - test 側は、各 fold の参照集合（train の 80%）で計算して平均する。参照集合の大きさを train 側とそろえ、test だけ近傍が近く出るずれを防ぐため
- **H5（スタッキング）**: 単体では E01 より大幅に悪い kNN（E07）や ExtraTrees（E08）を加えて統合すると、5 fold すべてで改善し、平均 -0.0301 となった。E09 と比べても -0.0151（5/5 fold）
  - 単体の精度が低くても、誤り方が違うモデルは統合に役立つ。上位解法が多様なモデルをそろえていた理由を確認できた
  - 実装は [`features.stack`](src/features.py)。1 段目の OOF 予測をそのまま 2 段目の特徴にし、2 段目は E01 と同じ LightGBM・同じ分割で学習する

### 注意点と Late での確認

CV 上は大きく改善したが、どちらにも OOF が楽観側に偏る要因があったため、Late で確かめた。

- E09: 学習行の距離特徴を作るときの参照集合に、検証 fold の行（とそのラベル）が含まれる。検証行自身の特徴には自分のラベルは入らないが、間接的なリークになりうる
- E10: 2 段目の学習行のメタ特徴は、検証 fold の行も含めて学習した 1 段目モデルの予測である（スタッキングで一般的な軽いリーク）
- E10: 2 段目は「単一モデルの OOF」で学習するが、テストでは「fold 平均の予測」を入力にする。P5 で、この形の違いが温度スケーリングを逆効果にしたのと同じ構造で、効果が目減りする可能性がある

| run | OOF | Public | Private | E01 との差（CV） | E01 との差（Private） | Public 順位相当 |
|---|---:|---:|---:|---:|---:|---:|
| E01 | 0.47393 | 0.45008 | 0.45151 | — | — | 709 / 3,509（上位 20.2%） |

- E06（温度スケーリング）と違い、E10 の 2 段目は fold 平均の入力でも崩れなかった。温度スケーリングは「確率の鋭さ」そのものを調整するため平均によるならし効果と打ち消し合ったが、スタッキングの 2 段目は主に「どのモデルをどのクラスで信じるか」を学ぶため、入力が多少ならされても影響が小さかったと考える（未検証の解釈）

## 追補: E09・E10 の nested 化と再測定（レビュー対応）

### 何が問題だったか

- E09: 距離特徴を全行について「自分の fold 以外を参照集合」として作ってから、同じ fold で LightGBM の CV をしていた。外側 fold 0 を検証するとき、学習側（fold 1〜4）の行の距離特徴は fold 0 の行とラベルを参照して作られている（cross-fold target leakage）
- E10: 2 段目の学習行のメタ特徴は、外側の検証 fold も学習に使った 1 段目モデルの予測だった。OOF を使うだけでは 2 段目の CV の独立性は保証されない

### 直したこと

- ラベルを使う特徴は、外側 fold ごとに学習行とそのラベルだけを受け取る形にした（[`pipeline.fold_inputs`](src/pipeline.py#L52)）。学習行の特徴は内側 4 fold の OOF、検証行・テスト行の特徴は内側の各参照集合（各モデル）での値の平均
- 距離特徴: [`features.KnnDistance`](src/features.py#L67)。スタッキング: [`stacking.Stacking`](src/stacking.py#L17)（1 段目を外側 fold ごとに内側 4 fold で学習し直す）
- label perturbation test（[`leak_check.py`](src/leak_check.py)）: 外側 fold 0 の検証行 12,376 件のラベルを別のクラスに変えても、学習・検証・テストの入力特徴が変わらないことを E11・E12・E13 で確認した
  - 対象は入力特徴まで。LightGBM は検証 fold で early stopping するので、学習済みモデルは検証ラベルに依存する（全実験共通の既知の偏り。P5 で +0.0020 程度と実測）
- 距離特徴のキャッシュは廃止した（nested 化しても計算は 1 run 4 分程度で、入力が変わったときに古いキャッシュを読む危険の方が大きい）
- リファクタ後のパイプラインで E01 を再計算し、保存済みの OOF と完全一致（最大差 0）、テスト予測の差が最大 3.3e-16 であることを確認した

- したがって、旧 E09 のリークによる楽観バイアスは、このデータでは 0.002 程度以下と見積もれる。ただし参照集合の大きさの違いと分けられていない

- E12（スタッキング）の E10 との差 -0.0027 も同じ構造（検証行の入力が内側 4 モデルの平均）と考えるが、stacking では切り分けていない

- E12 は外部評価として提出した: Public 0.42170（235 / 3,509 相当、上位 6.7%）、Private 0.42356。CV は E10 より -0.0027 良いが、Private は E10（0.42209）より +0.0015 悪い
  - 解釈: nested 版の提出は、1 段目を各外側 fold の内側（train の 60%）で学習したモデルの平均でテストの入力を作る。旧 E10 は 1 段目を train の 80% で学習していた。1 段目の学習量が少ない分、テストの入力が弱くなったと考える（未検証）
  - リークは CV の推定にだけ影響し、提出物そのものを不正にするわけではない。CV の推定は nested で行い、提出用の 1 段目は多くのデータで学習する構成が合理的と考える

## 追補: MLP（NN）の 1 系統

上位解法の中心だった NN を、scikit-learn の `MLPClassifier` で 1 系統だけ試した（[`models.mlp`](src/models.py#L98)）。2 層（256-128、ReLU）、Adam、学習率 1e-3、L2 1e-4、batch 256。early stopping は学習 fold 内の 10% で行い、検証 fold のラベルは使わない。標準化は Pipeline 内で学習 fold だけで fit する。

|---|---|---|---:|---:|

- **MLP 単体は LightGBM に大きく負けた**。過信気味（T* 1.31）だが、較正しても 0.5225 で、弱さは較正だけではない。約 25 epoch で early stopping し、fold 1 だけ 0.598 と不安定。dropout がなく、bagging もしていない。上位解法（dropout + 120 回以上の bagging）とは条件がかなり違う
- **H1 の NN 版は不支持**: 標準化した MLP では log1p の効果は見られなかった（+0.0023、改善 1/5）。標準化と ReLU の組み合わせで、裾の長さの影響はすでに小さいのかもしれない（未検証）
- **NN と GBDT の相補性は支持**: 単体で弱い MLP も、1 段目に加えると 5/5 fold で改善した（-0.0036）。行損失の相関は E01 と 0.766 で、kNN（0.746）と同程度に誤り方が違う
- E16 は CV の最良（0.43747）。最終モデルとして 1 回だけ外部評価した: Public 0.41966（187 / 3,509 相当、上位 5.3%）、Private 0.42112。E12 比で Private -0.0024（CV では -0.0036）で、MLP の追加効果は Late でも同じ向きに残った。旧 E10（0.42209）も上回った

### 統計的な解釈の注意

- 「5/5 fold で改善」は強い補助証拠だが、fold 同士は学習データの 3/4 を共有しており、独立した 5 回の再現ではない。統計的に有意とは主張しない
- 差の小さい比較（E09 → E13 の +0.0019 など）は、seed を変えた CV や行単位の損失差の bootstrap で確かめていない（未検証）
