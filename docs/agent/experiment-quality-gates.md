# 実験の Quality Gate

新規コンペでは、CV の公開・モデル選定・最終 export を `kumite.quality_gates` の入口に接続する。`dev new` が作る `quality-gates.toml` が有効化の目印になる。有効なコンペの `RunStore` は CV 証跡を伴わない公開を拒否する。

## 実行時点

| 段階 | 実行する検査・準備 |
|---|---|
| P0 | 公式指標の向き・評価単位・提出形式を確認する。採点疎通のダミー提出は選定候補に入れない。 |
| P1 | 目的変数、評価 ID、集約キー、予測の形と範囲、欠損の意味を決める。 |
| P2 | データのハッシュと分割を固定し、ラベル独立性、OOF の網羅性、指標の小規模テストを用意する。候補の run ID・優先順・同点許容差を実験前に定める。候補計画を変更するときは理由を記録して別の選定記録にする。 |
| P3 | Baseline の学習前に `reserve_cv`、学習後に `publish_gated_cv` を通す。必要なら Baseline の選定記録を作り、同じ export Gate で初回提出を生成する。 |
| P4 | 各実験で学習前と公開時の CV Gate を繰り返す。派生 run は依存成果物を宣言する。比較前に候補の OOF を再採点する。 |
| P5 | 上位解法の調査を記録する。新たに検証する候補は P6 の学習前に計画へ反映する。 |
| P6 | 新しい各候補に P4 と同じ検査を適用する。 |
| P7 | 全候補の証跡を検査して選定記録を保存する。最終 export の入口で記録を再検証し、コード・設定が一致した場合に限り全量学習または提出ファイルの生成を開始する。 |
| P8 | CV の run ID、選定記録、export ID、外部評価の対応を報告書に残す。 |

`dev check` は既存の `tests/` 実行経路で共通 Gate のテストを実行する。コンペ固有のテストは同じコマンドのコンペ別プロセスで実行する。共通テストと ASHRAE の統合テストは小さな合成データを使う。実データに対する Gate は学習・選定・export の各入口で実行する。

## 入出力契約

### 学習と CV 公開

1. 利用する依存を `RunStore.input_hashes(parent, *names)` で `{"run_id/ファイル名": ハッシュ}` にする。依存の読み出しには `artifact_path` または `load_array` を使う。
2. `SourceSpec(root, files, settings)` に、CV と export で共有するコードのファイル一覧と実効設定を渡す。モデル、特徴量、前処理、評価・閾値・推論のコードと、使用する共有モジュール、設定ファイル、依存ロックファイルを対象にする。パスは root 相対の POSIX 形式。設定は JSON にできる値とし、学習と export が同じ設定オブジェクトを参照する。CV と全量学習で異なる処理は共有ソースに両方の入口を置き、ラウンド数などの変換規則を設定またはコードに固定する。
3. `with reserve_cv(store, run_id, source, inputs) as (reservation, start):` の中で学習する。予約後に親のログと実ファイル、推移的な依存と循環を検査し、ファイルの SHA-256 と実効設定を採取する。
4. 同じ予約の中で `publish_gated_cv(store, reservation, record, write, source=source, before_training=start, assess=assess)` を呼ぶ。保存用一時ディレクトリから OOF を再採点し、fold 別・全体のスコアを絶対誤差 1e-12 で照合する。依存宣言と実ファイル、学習前後のソース・設定も照合する。成功時は実験ログの不変項目、成果物一覧とハッシュ、ソースと設定を `cv_evidence.json` に封入する。確定処理は `RunStore` を使う。
5. 行順 OOF で既存の `publish_cv_run` を使う場合は `gate=(source, start, expected_oof_shape)` を渡す。分割ハッシュに `array_sha256(split_roles(n_rows, splits))` を使う。期待形状は評価仕様から決める。クエリ予測の形状、確率の範囲・和、提出ファイルの行 ID と順序はコンペ側で検査する。

### OOF アダプター

`AssessOOF` はハッシュ照合済み成果物への名前ベースの参照関数と `ExperimentRecord` を受け取り、fold 順スコアと全体スコアを返す。公開時は同じ名前参照で一時ファイルを読み直す。正本データから評価対象、分割、指標を確かめ、成果物の形状・ID・値域・件数を採点の前に検証する。評価用の入力ハッシュは現在の正本から計算する。採点アダプターの契約は候補間で共通にする。

- 行単位と時系列では `dense_oof` を使える。分割・データハッシュと完全な形状を照合し、検証行には有限値、検証対象外には NaN を要求する。
- 画像検出なら、期待する画像 ID ごとに検証 fold と予測を突き合わせる。検出ゼロの画像も明示的に記録し、重複・欠落・未知の ID を拒否して画像単位の公式指標を計算する。
- F1 なら、確率や予測スコアから事前に定めた閾値決定手順を再現し、保存された閾値があれば照合する。外側 fold の評価に適用する閾値は外側学習側から決める。全 OOF ラベルで閾値を最適化した値を外側 CV の評価値に使わない。
- 週別集約なら、行 ID と週キーを正本と照合し、評価週の欠落・重複と集約順序を検査してから指標を計算する。fold スコアの平均と全体指標は別々に計算する。

### 選定と export

- `SelectionPlan(candidates, tolerance)` には候補を優先順で全件指定する。`select_runs` は勝敗に関係なく全候補で成果物・依存・ログ・再計算スコアを検査する。既存の `compare_runs` で評価条件を照合したうえで、最良の再計算値から許容差以内の最初の候補を選ぶ。
- `write_selection` で候補、許容差、再計算値、勝者と CV 証跡ハッシュを新規ファイルに保存する。`verify_selection` には選定記録とは独立した事前計画を渡す。欠落や不一致は例外になり、候補を除外して続行することはない。
- `publish_export(store, export_id, plan=..., receipt=..., assess=..., source=..., write=..., required_outputs=(... ,))` を最終 export の入口にする。選定を再実行して記録を照合し、選定済み CV のソースと実効設定を検査してから、勝者の実験記録と一時ディレクトリを `write` に渡す。`write` は指定された勝者と照合済み設定で学習・推論し、提出内容を検査して一時ディレクトリに書く。公開時に必須ファイル、ソース・設定、依存を再確認する。
- export の成果物と監査ログは `outputs/exports/` 内の `RunStore` に保存する。選定記録、ソース証跡、候補の成果物ハッシュが残る。export 監査ログ内の CV スコアは選定済み CV からの参照値。提出には確定済み export 内のファイルを使う。

## 既存の保証と適用範囲

- `RunStore` は予約の排他、run ID の再利用拒否、一時ディレクトリからの公開、ログの確定と失敗時の復旧、読み込み時の成果物ハッシュ照合を担う。
- `provenance` はファイル・配列の SHA-256 と作業ツリーを反映した Git バージョンを採取する。CV と export では実効設定と個別のソースファイルを別途照合する。
- `crossfit` は分割の空・範囲外・重複・学習検証の重なりを拒否し、fold 予測の形と有限性を検査する。`cv_run` は既に fold 別と検証行全体のスコアを記録する。Gate の独立した再採点は、ディスクに保存された予測と記録の整合性を確かめる。
- 既存コンペは従来の公開経路を使える。`cv_evidence.json` がない既存 run は厳格な選定で拒否する。従来のコンペで既存成果物を派生 run の入力にする場合は、宣言した成果物のハッシュと既存ログの依存宣言までが検査対象になる。Gate が有効なコンペでは依存する CV run にも CV 証跡が必要。従来の選定結果は維持し、厳格な証跡が必要なときは新しい ID で実行する。
- 保証の範囲は申告された入力・ソースと正本に照合するアダプターで決まる。コード・設定・ログを一式置換する権限を持つ第三者、実行途中に改変して元に戻す操作、未宣言の依存、検査を迂回する独自 export は対象外。ラベルリークの設計検査や提出先での採点は別途行う。
